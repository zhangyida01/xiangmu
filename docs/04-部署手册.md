# 部署手册（CentOS 7.9 + Docker Compose）

> 适用版本：delivery-server 1.0.0 ｜ 配套文档：docs/01 功能清单、docs/02 数据库设计、docs/03 接口设计
> 目标：在一台 CentOS 7.9 虚拟机上，用 Docker Compose 跑起「MySQL + 应用」单容器单端口的交付管理后台。
>
> **怎么读这份手册**
> - 第一次部署：从第〇章按顺序做到第九章验收，全程约 40～90 分钟（其中构建占 5～15 分钟）。
> - 日常运维：直接看第十二章命令速查。
> - 出问题：先看第十五章 FAQ，再 `docker compose logs app`。
> - 只想三步跑起来：看 `deploy/README.md`。

## 〇、先看这一章：架构、端口与准备工作

### 0.1 部署架构

```
  你的电脑浏览器
        │  http://虚拟机IP:8080        （或启用 nginx 后 https://虚拟机IP）
        ▼
┌──────────────────────────── CentOS 7.9 虚拟机 ────────────────────────────┐
│                                                                          │
│  ┌─ 容器 pdm-app ─────────────────────┐   ┌─ 容器 pdm-mysql ────────────┐ │
│  │ Spring Boot 3 (JRE 17)             │   │ MySQL 8.0                   │ │
│  │  ├ 后端 REST API  /api/**          │   │  └ 库 pdm（Flyway 建表）    │ │
│  │  └ 前端静态资源（打进 jar/static）  │   │                             │ │
│  │ 监听 8080                          │   │ 监听 3306                   │ │
│  └───────┬────────────────────────────┘   └──────┬──────────────────────┘ │
│          │  宿主机发布 ${APP_LISTEN}:8080          │  宿主机发布 127.0.0.1:3306
│          │                                       │  （只有虚拟机能连）
│          ▼                                       ▼
│  /data/pdm/uploads  /data/pdm/logs       /data/pdm/mysql
│  /data/pdm/keys/master.key（只读挂载）
└──────────────────────────────────────────────────────────────────────────┘
```

要点：

- 前端 Vue 打包产物在**镜像构建阶段**被塞进 jar 的 `src/main/resources/static/`，运行时只有一个容器、一个端口，不需要单独部署 nginx 或 Node。
- 数据库端口只发布到 `127.0.0.1`，局域网内其他机器连不上，只有 app 容器通过 compose 内部网络访问。
- 凭据密码在写库前用 AES-256-GCM 加密，密钥来自宿主机文件 `/data/pdm/keys/master.key`，容器内**只读**挂载，不入库、不进镜像、不进备份。
- 附件（交付文档 + 凭据加密附件）都落在宿主机 `/data/pdm/uploads`，容器重建不丢数据。

### 0.2 端口、目录、命名总览

| 类别 | 值 | 说明 |
| --- | --- | --- |
| Web 端口 | 容器内 `8080`；宿主机发布端口默认 `8080` | 发布地址由 `APP_LISTEN`、宿主机端口由 `APP_PORT` 决定 |
| MySQL 端口 | `3306` | 只发布到 `127.0.0.1`，外部不可达 |
| nginx 端口 | `80` / `443` | 可选，默认注释掉 |
| 代码目录 | `/opt/pdm/src` | 仓库根目录，可换成任意路径 |
| compose 目录 | `/opt/pdm/src/deploy` | 所有 `docker compose` 命令都在这里执行 |
| 环境变量文件 | `/opt/pdm/src/deploy/.env` | 权限 600，不提交 git |
| 数据库数据 | `/data/pdm/mysql` | 属主 `999:999`（mysql 容器内用户） |
| 附件存储 | `/data/pdm/uploads` | 属主 `1000:1000`（app 容器内用户 pdm） |
| 应用日志 | `/data/pdm/logs` | 属主 `1000:1000` |
| 主密钥 | `/data/pdm/keys/master.key` | 权限 `600`、属主 `1000:1000`（容器内 app 用户）；root 仍可读写 |
| 备份产物 | `/data/pdm/backup/{db,files}` | 属主 `1000:1000` |
| 镜像名 | `pdm/delivery-server:1.0.0` | compose 里 `image:` 指定 |
| 容器名 | `pdm-app` / `pdm-mysql` / `pdm-nginx` | 固定名，方便 `docker exec` |
| 容器内运行用户 | `pdm`（uid/gid = 1000） | 非 root |
| compose 网络 | `deploy_default` | 项目名取自所在目录名 `deploy` |

### 0.3 虚拟机资源要求

| 资源 | 最低 | 建议 | 备注 |
| --- | --- | --- | --- |
| CPU | 2 核 | 4 核 | 构建阶段吃 CPU，运行时很闲 |
| 内存 | 2 GB | 4 GB | **构建时** node + maven 同时跑，2 GB 可能 OOM；运行时 app 约占 500～800 MB，MySQL 约 400 MB |
| 磁盘 | 20 GB 空闲 | 40 GB 空闲 | 基础镜像约 1.5 GB，构建缓存与中间层可能再占 3～6 GB |
| 系统 | CentOS 7.9 x86_64 | 同左 | 内核 3.10，Docker 用 overlay2 |
| 网络 | 能访问 Docker Hub 与 Maven Central | 同左 | 不满足则走第十四章离线路径 |

内存只有 2 GB 时的应对：先给虚拟机加 swap（构建完可删）：

```bash
dd if=/dev/zero of=/swapfile bs=1M count=2048
chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
free -h          # 确认 Swap 一行有 2.0Gi
```

### 0.4 两条部署路径，先选一条

| | 路径 A：在线构建（推荐） | 路径 B：离线导入 |

## 一、宿主机前置检查

### 1.1 确认系统信息

```bash
cat /etc/redhat-release      # 期望：CentOS Linux release 7.9.2009
uname -r                     # 期望：3.10.x-xxx.el7.x86_64
arch                         # 期望：x86_64（镜像与构建机架构必须一致）
id                           # 确认当前是 root 或有 sudo 权限
```

### 1.2 时间同步（必做，别跳过）

时间不准会导致两个隐蔽故障：JWT 刚签发就判定过期（登录死循环）、备份文件名日期错乱。

```bash
timedatectl set-timezone Asia/Shanghai
timedatectl set-ntp true
systemctl enable --now chronyd
chronyc sources -v           # 看是否有 ^* 开头的可用时间源
timedatectl                  # 确认 System clock synchronized: yes
```

内网无 NTP 服务器时，手工对时并关掉 NTP：

```bash
timedatectl set-ntp false
timedatectl set-time '2026-10-10 09:30:00'
```

### 1.3 磁盘与内存

```bash
free -h                      # 可用内存建议 >= 2G
df -h /var/lib/docker /data  # 两个目录所在盘的空闲空间
```

`/var/lib/docker` 与 `/data` 在同一个盘也没关系，但要保证合计空闲 ≥ 20 GB。

### 1.4 SELinux（CentOS 7 高频坑）

```bash
getenforce                   # Enforcing / Permissive / Disabled
```

本项目的 `deploy/docker-compose.yml` 已给所有 bind mount 加了 `:z` 后缀，Docker 会自动把宿主机目录重标记为 `container_file_t`，**SELinux 保持 Enforcing 也能正常读写**，通常不需要额外操作。

如果仍然遇到「Permission denied」写不进 `/data/pdm/uploads`、或 MySQL 初始化失败，先确认是不是 SELinux 拦的：

```bash
ausearch -m avc -ts recent | tail -20        # 有输出就是 SELinux 拒绝
ls -Zd /data/pdm/uploads /data/pdm/mysql     # 期望看到 container_file_t
```

手工修标签（等价于 `:z` 的效果）：

```bash
yum install -y policycoreutils-python        # 提供 semanage / restorecon
semanage fcontext -a -t container_file_t '/data/pdm(/.*)?'
restorecon -Rv /data/pdm
```

> 不建议直接 `setenforce 0` 关掉 SELinux。真要先排除干扰，可以临时 `setenforce 0` 验证一次，确认是它之后再按上面的方式正确打标签，然后 `setenforce 1` 恢复。

### 1.5 yum 是否可用

```bash
yum makecache fast
```

报 `404 Not Found` / `Cannot find a valid baseurl for repo` → CentOS 7 已 EOL，去第二章修复源。
命令正常返回 → 可以直接跳到第三章。

## 二、修复 yum 源（CentOS 7 EOL 后必须）

CentOS 7 于 2024-06-30 停止维护，官方 `mirrorlist.centos.org` 已下线，默认的 `CentOS-Base.repo` 会全部 404。

### 2.1 切换到 vault 归档源

```bash
# 1) 备份原有 repo，别直接删
mkdir -p /etc/yum.repos.d/bak
mv /etc/yum.repos.d/CentOS-*.repo /etc/yum.repos.d/bak/

# 2) 写入 vault 源
cat > /etc/yum.repos.d/CentOS-Base.repo <<'EOF'
[base]
name=CentOS-7 - Base
baseurl=https://vault.centos.org/7.9.2009/os/$basearch/
gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-CentOS-7

[updates]
name=CentOS-7 - Updates
baseurl=https://vault.centos.org/7.9.2009/updates/$basearch/
gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-CentOS-7

[extras]
name=CentOS-7 - Extras
baseurl=https://vault.centos.org/7.9.2009/extras/$basearch/
gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-CentOS-7
EOF

# 3) 刷新缓存
yum clean all && yum makecache
```

`vault.centos.org` 在国外，慢的话换阿里云归档镜像（把上面三处 `https://vault.centos.org/7.9.2009` 换成 `https://mirrors.aliyun.com/centos-vault/7.9.2009`）：

```bash
sed -i 's#https://vault.centos.org/7.9.2009#https://mirrors.aliyun.com/centos-vault/7.9.2009#g' /etc/yum.repos.d/CentOS-Base.repo
yum clean all && yum makecache
```

### 2.2 完全无外网：挂载 ISO 做本地源

```bash
mkdir -p /mnt/cdrom
mount -o loop /path/to/CentOS-7-x86_64-DVD-1908.iso /mnt/cdrom

cat > /etc/yum.repos.d/local.repo <<'EOF'
[local]
name=CentOS-7 Local ISO
baseurl=file:///mnt/cdrom
enabled=1
gpgcheck=0
EOF

# 让其他源全部失效，避免 yum 仍去连外网
yum-config-manager --disable base updates extras 2>/dev/null || true
yum clean all && yum makecache
```

开机自动挂载（否则重启后源失效）：

```bash
echo '/path/to/CentOS-7-x86_64-DVD-1908.iso /mnt/cdrom iso9660 loop,ro 0 0' >> /etc/fstab
```

> 无外网时 Docker 也得离线装：从 ISO 里没有 docker-ce，需要另外下载 rpm 包（见第十四章）。

## 三、安装 Docker 与 Compose 插件

### 3.1 安装

CentOS 7 内核 3.10，官方支持的最高版本是 docker-ce 24.x；25+ 需要更新内核。**指定版本号安装更稳妥**，别直接 `yum install docker-ce` 让它挑最新。

```bash
# 卸载可能存在的旧版
yum remove -y docker docker-client docker-client-latest docker-common \
              docker-latest docker-latest-logrotate docker-logrotate docker-engine podman runc

# 装工具与依赖
yum install -y yum-utils device-mapper-persistent-data lvm2

# 加 Docker 官方源（国内慢就换阿里云，见下）
yum-config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo

# 看有哪些可用版本，挑一个 24.x
yum list docker-ce --showduplicates | sort -r | head -10

# 安装（版本号按上一步实际输出调整）
yum install -y docker-ce-24.0.7 docker-ce-cli-24.0.7 containerd.io docker-compose-plugin
```

官方源慢或超时，换阿里云：

```bash
yum-config-manager --add-repo https://mirrors.aliyun.com/docker-ce/linux/centos/docker-ce.repo
```

完全无外网：在能联网的机器上下载 rpm 后拷贝过来安装（见第十四章 14.4）。

### 3.2 启动并设为开机自启

```bash
systemctl enable --now docker
systemctl status docker --no-pager | head -5
docker version                # Client 与 Server 都要有输出
docker compose version        # 期望 v2.x（不是 docker-compose v1）
docker run --rm hello-world   # 能拉取并运行说明一切正常
```

> 本手册全部使用 `docker compose`（v2 子命令），不是老的 `docker-compose`（v1 已停止维护，语法有差异）。

### 3.3 检查 overlay2 前置条件（XFS 必须 ftype=1）

CentOS 7 默认 XFS 文件系统，如果建分区时 `ftype=0`，overlay2 存储驱动**无法工作**，Docker 会启动失败或运行异常。

```bash
df -T /var/lib/docker                       # 看文件系统类型
xfs_info /var/lib/docker | grep ftype       # 期望 ftype=1
```

如果输出 `ftype=0`，只能重建分区（数据会丢，趁还没部署赶紧做）：

```bash
systemctl stop docker
# 假设新分区是 /dev/sdb1，按实际设备名改
mkfs.xfs -n ftype=1 -f /dev/sdb1
mkdir -p /data/docker
mount /dev/sdb1 /data/docker
echo '/dev/sdb1 /data/docker xfs defaults 0 0' >> /etc/fstab
```

然后把 Docker 数据目录指过去（见 3.4 的 `daemon.json` 里的 `data-root`）。

### 3.4 配置 daemon.json（日志上限 + 镜像加速）

不做日志上限，容器日志会无限增长把磁盘吃满。

```bash
mkdir -p /etc/docker
cat > /etc/docker/daemon.json <<'EOF'
{
  "data-root": "/var/lib/docker",
  "log-driver": "json-file",
  "log-opts": { "max-size": "50m", "max-file": "3" },
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://dockerproxy.com"
  ],
  "live-restore": false
}
EOF

systemctl daemon-reload
systemctl restart docker
docker info | grep -A3 'Registry Mirrors'
```

字段说明：

| 字段 | 作用 |
| --- | --- |
| `data-root` | Docker 镜像与容器数据目录；做了 3.3 的分区迁移就改成 `/data/docker` |
| `log-driver` / `log-opts` | 单个容器日志最大 50 MB，最多保留 3 个文件 |
| `registry-mirrors` | 国内镜像加速；能直连 Docker Hub 可以删掉这一段 |
| `live-restore` | 保持 `false`：本项目用 compose 管理，重启 docker 时让容器一起重启更简单 |

改完 `daemon.json` 必须 `systemctl restart docker`，已运行的容器会被重启。

### 3.5 可选：让普通用户免 sudo 使用 docker

```bash
usermod -aG docker 你的用户名
newgrp docker            # 或重新登录
docker ps
```

> 安全提示：`docker` 组等价于 root 权限（可以挂载宿主机根目录）。个人自用机可以接受，多人共用的机器建议保持 sudo。

## 四、目录与主密钥准备

### 4.1 创建宿主机目录

```bash
mkdir -p /data/pdm/{mysql,uploads,keys,logs,backup/db,backup/files}
mkdir -p /opt/pdm/src
mkdir -p /opt/pdm/nginx/certs      # 只在启用 HTTPS 时用得到，先建着无妨

ls -ld /data/pdm/*
```

> `/data/pdm/mysql` **必须为空**，否则 MySQL 容器会认为数据目录已初始化，跳过建库，导致应用连不上。

### 4.2 生成凭据加密主密钥

这是整个系统最关键的一个文件：所有平台账号密码都用它加密后存进 MySQL。

```bash
openssl rand -base64 32 > /data/pdm/keys/master.key
chown 1000:1000 /data/pdm/keys/master.key
chmod 600 /data/pdm/keys/master.key

cat /data/pdm/keys/master.key      # 44 个字符的 Base64 串
ls -l /data/pdm/keys/master.key    # -rw------- 1 1000 1000（宿主机上 1000 可能显示为某个用户名）
```

应用启动时会校验：文件必须存在、必须是 Base64、解码后必须正好 32 字节，否则直接拒绝启动并在日志里给出明确提示。

**属主必须是 `1000:1000`**：容器内 app 以 uid 1000 运行，只读挂载不改变属主；若文件是 `root:root` + `600`，应用读不到会直接 `AccessDeniedException` 起不来。

### 4.3 设置属主（为什么是 1000 和 999）

容器内进程的用户与宿主机文件属主必须匹配，否则写不进去：

| 目录 | 属主 | 原因 |
| --- | --- | --- |
| `/data/pdm/uploads` | `1000:1000` | app 容器内以 `pdm` 用户运行，Dockerfile 里 `useradd -u 1000` |
| `/data/pdm/logs` | `1000:1000` | 同上，Spring Boot 要写 `delivery-server.log` |
| `/data/pdm/backup` | `1000:1000` | 备份脚本以当前用户写文件 |
| `/data/pdm/mysql` | `999:999` | mysql:8.0.32 官方镜像内 `mysql` 用户的 uid/gid 是 999 |
| `/data/pdm/keys` | `root:root`，文件 600 | 容器只读挂载，只要「可读」不要「可写」 |

```bash
chown -R 1000:1000 /data/pdm/uploads /data/pdm/logs /data/pdm/backup
chown -R 999:999  /data/pdm/mysql
chmod 700 /data/pdm/keys

# 验证
ls -ln /data/pdm
```

> 只读的 keys 目录为什么不给 1000？因为容器只需要读它。保持 root 属主 + 600 意味着即使容器被攻破，也改不了密钥。

### 4.4 立刻做主密钥离线备份（现在就做，别拖）

```bash
cat /data/pdm/keys/master.key
```

把这串字符抄到**至少两个**与服务器分开保管的地方，例如：

- 你自己电脑上的密码管理器（ KeePass / Bitwarden / 1Password ）里新建一条「PDM master.key」；
- 一张纸放进抽屉，或一个加密 U 盘。

**后果说明**：

| 情况 | 结果 |
| --- | --- |
| 数据库备份在，master.key 也在 | 完整恢复，凭据可正常解密 |
| 数据库备份在，master.key 丢了 | 项目/文档/审计都能恢复，**但所有已存的账号密码永久无法解密**，只能逐条重新录入 |
| master.key 换了新的 | 同上，旧密文全部作废 |

所以：**主密钥一旦生成就不要更换**。真要更换，必须先把所有凭据用旧密钥解密、再用新密钥重新加密（阶段二可做「密钥轮换」功能）。

## 五、把代码放到虚拟机上

仓库在你 Windows 电脑上，先传到虚拟机的 `/opt/pdm/src`。三种方式任选一种。

### 5.1 方式 A：git clone（推荐，升级最省事）

如果代码已推到 GitHub / Gitee / 内网 GitLab：

```bash
yum install -y git
cd /opt/pdm
git clone <你的仓库地址> src
cd src && ls
```

后续升级只需 `git pull`（见第十三章）。

私有仓库需要认证：

```bash
git config --global credential.helper store
git clone https://用户名:访问令牌@github.com/you/repo.git src
```

### 5.2 方式 B：Windows 打包 + scp 上传

### 5.3 方式 C：WinSCP / VMware 共享文件夹

## 六、配置 .env（每一项都要改）

### 6.1 生成强随机口令

```bash
# 数据库口令（24 位，去掉了容易混淆的字符）
openssl rand -base64 24 | tr -d '/+=' | cut -c1-24

# JWT 签名密钥（必须 >= 64 字符；HS256 要求密钥长度不低于摘要长度）
openssl rand -base64 48 | tr -d '\n=' | cut -c1-64

# 管理员初始密码（首登会强制改，可以简单点，但别用弱口令）
openssl rand -base64 12 | tr -d '/+=' | cut -c1-12 ; echo '@1'
```

### 6.2 创建 .env

```bash
cd /opt/pdm/src/deploy
cp .env.example .env
vi .env                 # 按 6.3 的说明逐项修改
chmod 600 .env          # 只有 root 可读
ls -l .env              # -rw------- 1 root root
```

### 6.3 变量逐项说明

| 变量 | 必填 | 示例 | 说明 |
| --- | --- | --- | --- |
| `MYSQL_ROOT_PASSWORD` | ✅ | 强随机 24 位 | MySQL root 口令。**只用于备份脚本和应急维护**，应用不用 root 连库 |
| `MYSQL_PASSWORD` | ✅ | 强随机 24 位 | 应用账号 `pdm` 的口令，会注入到 app 容器的 `DB_PASSWORD` |
| `DB_NAME` | ⬜ | `pdm` | 数据库名，MySQL 容器首次启动会自动创建 |
| `DB_USER` | ⬜ | `pdm` | 应用连接库的账号，MySQL 容器首次启动会自动创建并授予 `DB_NAME` 的全部权限 |
| `JWT_SECRET` | ✅ | 64 位随机串 | 登录令牌签名密钥。**改了之后所有已登录用户会被强制重新登录** |
| `INIT_ADMIN_PASSWORD` | ⬜ | `Admin@12345` | 首次启动创建 `admin` 账号用的初始密码，要求 ≥8 位且含字母和数字。不满足策略时应用会退回默认值并打 WARN 日志 |
| `CAPTCHA_ENABLED` | ⬜ | `true` | 登录图形验证码开关。内网自用嫌麻烦可以设 `false` |
| `APP_LISTEN` | ⬜ | `0.0.0.0` | Web 端口发布地址。`0.0.0.0` = 局域网可访问；`127.0.0.1` = 只有虚拟机本机能访问（此时需配 SSH 隧道或 nginx） |
| `APP_PORT` | ⬜ | `8080` | 宿主机发布端口（容器内固定 8080）。宿主机 8080 被占用时改这里，例如 `8082`，访问地址随之变为 `http://虚拟机IP:8082` |
| `APP_MEM_LIMIT` | ⬜ | `1g` | app 容器内存上限。JVM 用 `-XX:MaxRAMPercentage=70` 按这个值算堆大小，虚拟机内存 ≥4G 可改成 `2g` |

一个填好的 `.env` 长这样：

```bash
MYSQL_ROOT_PASSWORD=Kq7mZx2Rt9Vb4Ns6Wp1Yc8Hg
MYSQL_PASSWORD=Df3jLa8Qu5Tn2Xw7Re4Vy9Bk
DB_NAME=pdm
DB_USER=pdm
JWT_SECRET=9f2c7a41e8b05d63fa19ce74b20d85a63f1c9e47b08d2a5f6c1e39b47a20d85f
INIT_ADMIN_PASSWORD=Xk4pQw7z@1
CAPTCHA_ENABLED=true
APP_LISTEN=0.0.0.0
APP_PORT=8080
APP_MEM_LIMIT=1g
```

### 6.4 三个容易踩的坑

1. **`.env` 里的值不要加引号**。`MYSQL_PASSWORD="abc"` 会把引号也算进密码，导致应用连库失败。
2. **密码里别用 `$`、`#`、空格**。compose 会把 `$` 当变量插值、`#` 当行内注释。真要用就写成 `$$`（compose 的转义）。上面的生成命令已经过滤掉这些字符。
3. **`.env` 必须和 `docker-compose.yml` 在同一目录**（都在 `deploy/` 下），compose 才会自动读取。用 `-f` 指定其他路径的 compose 文件时，要同时用 `--env-file` 指定 `.env`。

`.env` 已在 `.gitignore` 里（`.env` 与 `*.env` 两条规则），不会被提交；`.dockerignore` 也排除了它，不会被打进镜像。

## 七、镜像与 Compose 编排

> 本章内容与仓库文件**逐字一致**，仅供理解与二次修改参考。文件已经写好，正常使用不需要动它们。

### 7.1 deploy/Dockerfile（三阶段构建）

前后端合并为**单容器单端口**部署：阶段 1 用 node 构建前端；阶段 2 把 `dist/` 拷进后端 `src/main/resources/static/` 再打 jar；阶段 3 只保留 JRE。所以构建上下文必须是**仓库根目录**，而不是 `delivery-server/`：

```bash
cd /opt/pdm/src          # 仓库根目录
docker build -f deploy/Dockerfile -t pdm/delivery-server:1.0.0 .
```

`deploy/docker-compose.yml` 里已配好 `build.context: ..` 与 `dockerfile: deploy/Dockerfile`，日常直接 `docker compose build` 即可，不必手工执行上面的命令。

```dockerfile
# 构建上下文必须是仓库根目录：docker build -f deploy/Dockerfile .
# 阶段 1：前端构建
FROM node:20-alpine AS web
WORKDIR /web
COPY delivery-web/package.json ./
RUN npm install --registry=https://registry.npmmirror.com --no-audit --no-fund
COPY delivery-web/ ./
RUN npm run build

# 阶段 2：后端构建，把前端产物塞进 jar 的 static 目录
FROM maven:3.9-eclipse-temurin-17 AS server
WORKDIR /build
COPY deploy/maven-settings.xml /root/.m2/settings.xml
COPY delivery-server/pom.xml ./
RUN mvn -B -q dependency:go-offline -DskipTests || true
COPY delivery-server/src ./src
COPY --from=web /web/dist ./src/main/resources/static
RUN mvn -B clean package -DskipTests

# 阶段 3：运行镜像
FROM eclipse-temurin:17-jre-jammy
ENV TZ=Asia/Shanghai LANG=C.UTF-8
# wget 供 HEALTHCHECK 使用（ubuntu jammy 基础镜像默认不带）；tzdata 保证容器时区正确
RUN apt-get update \
    && apt-get install -y --no-install-recommends wget tzdata \
    && ln -snf /usr/share/zoneinfo/$TZ /etc/localtime && echo $TZ > /etc/timezone \
    && rm -rf /var/lib/apt/lists/* \
    && useradd -u 1000 -m pdm \
    && mkdir -p /app/logs /app/uploads /app/keys
WORKDIR /app
COPY --from=server /build/target/delivery-server.jar /app/app.jar
RUN chown -R pdm:pdm /app
USER pdm
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=5s --start-period=90s --retries=3 \
  CMD wget -qO- http://127.0.0.1:8080/api/system/health || exit 1
ENTRYPOINT ["java","-XX:MaxRAMPercentage=70","-Djava.security.egd=file:/dev/./urandom","-jar","/app/app.jar"]
```

逐段说明：

| 阶段 | 基础镜像 | 做什么 | 为什么 |
| --- | --- | --- | --- |
| `web` | `node:20-alpine` | `npm install` + `npm run build` 产出 `dist/` | Element Plus + Vite 需要 Node 18+，20 是 LTS |
| `server` | `maven:3.9-eclipse-temurin-17` | 先 `dependency:go-offline` 预热依赖，再拷 `src` 与前端 `dist`，最后 `package` | 先拷 pom 再拉依赖，能让「只改了代码」的二次构建命中缓存，快很多 |
| 运行 | `eclipse-temurin:17-jre-jammy` | 只放 `app.jar`，装 `wget`/`tzdata`，建 `pdm` 用户 | 最终镜像不含 Maven、Node 与源码，体积小、攻击面小 |

几个细节：

- `npm install --registry=https://registry.npmmirror.com`：国内网络直连 npmjs 常常超时，这里固定走淘宝镜像。想换回官方源删掉这个参数即可。
- `mvn dependency:go-offline ... || true`：个别插件解析失败时不中断构建，最终 `package` 阶段仍会把依赖拉全。
- `useradd -u 1000 -m pdm` + `USER pdm`：容器内非 root 运行，uid 固定 1000，与第四章的宿主机属主对应。
- `/app/keys`、`/app/uploads`、`/app/logs` 三个目录在镜像里预建，运行时被宿主机目录覆盖挂载。
- `HEALTHCHECK` 每 30 秒探一次 `/api/system/health`（该接口免鉴权），`start-period=90s` 给足启动时间，所以刚启动时短暂显示 `starting` 是正常的。
- `-XX:MaxRAMPercentage=70`：JVM 堆最多用容器可见内存的 70%，避免被 OOMKilled。
- 后端依赖默认走 `deploy/maven-settings.xml` 的阿里云公共镜像（`mirrorOf=central`），与前端 npmmirror 同理；境外部署想直连 Maven Central，删掉 Dockerfile 里那行 `COPY deploy/maven-settings.xml ...` 即可。

### 7.2 deploy/docker-compose.yml

```yaml
services:
  mysql:
    # 钉死 8.0.32：更新的 8.0.x 官方镜像基于 Oracle Linux 9，glibc 要求 CPU 支持 x86-64-v2，
    # 老虚拟化平台（vCPU 只暴露 baseline）会 Fatal glibc error 直接起不来；8.0.32 基于 OL8，v1 CPU 可跑
    image: mysql:8.0.32
    container_name: pdm-mysql
    restart: always
    command:
      - --character-set-server=utf8mb4
      - --collation-server=utf8mb4_general_ci
      - --default-time-zone=+08:00
      - --max_connections=200
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
      MYSQL_DATABASE: ${DB_NAME:-pdm}
      MYSQL_USER: ${DB_USER:-pdm}
      MYSQL_PASSWORD: ${MYSQL_PASSWORD}
      TZ: Asia/Shanghai
    volumes:
      # 数据落在宿主机，容器重建不丢；:z 让 SELinux 打上容器可读写标签（CentOS 7 Enforcing 时必需）
      - /data/pdm/mysql:/var/lib/mysql:z
    ports:
      # 数据库只绑回环，任何外部机器都连不上，无需在防火墙处理
      - "127.0.0.1:3306:3306"
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-uroot", "-p${MYSQL_ROOT_PASSWORD}"]
      interval: 10s
      timeout: 5s
      retries: 12
      start_period: 40s

  app:
    image: pdm/delivery-server:1.0.0
    build:
      context: ..
      dockerfile: deploy/Dockerfile
    container_name: pdm-app
    restart: always
    # 必须给容器设内存上限：JVM 用 -XX:MaxRAMPercentage=70 算堆大小，
    # 不设上限它会按宿主机总内存的 70% 来算，容易和 MySQL 抢内存被 OOMKilled
    mem_limit: ${APP_MEM_LIMIT:-1g}
    mem_reservation: 512m
    depends_on:
      mysql:
        condition: service_healthy
    environment:
      TZ: Asia/Shanghai
      SPRING_PROFILES_ACTIVE: prod
      DB_HOST: mysql
      DB_PORT: "3306"
      DB_NAME: ${DB_NAME:-pdm}
      DB_USER: ${DB_USER:-pdm}
      DB_PASSWORD: ${MYSQL_PASSWORD}
      PDM_MASTER_KEY_FILE: /app/keys/master.key
      PDM_UPLOAD_DIR: /app/uploads
      PDM_JWT_SECRET: ${JWT_SECRET}
      PDM_INIT_PASSWORD: ${INIT_ADMIN_PASSWORD:-Admin@12345}
      PDM_CAPTCHA_ENABLED: ${CAPTCHA_ENABLED:-true}
    volumes:
      - /data/pdm/uploads:/app/uploads:z
      - /data/pdm/logs:/app/logs:z
      # 主密钥只读挂载：容器内改不了，泄露面更小
      - /data/pdm/keys:/app/keys:ro,z
    ports:
      # 需要从自己电脑的浏览器访问就得绑 0.0.0.0；只在虚拟机本机访问改成 127.0.0.1；启用 nginx 后可整段删掉
      - "${APP_LISTEN:-0.0.0.0}:${APP_PORT:-8080}:8080"

  # 需要 HTTPS 时取消注释，并准备 /opt/pdm/nginx/certs 下的证书
  # nginx:
  #   image: nginx:1.25-alpine
  #   container_name: pdm-nginx
  #   restart: always
  #   depends_on: [app]
  #   ports:
  #     - "80:80"
  #     - "443:443"
  #   volumes:
  #     - ./nginx/conf.d:/etc/nginx/conf.d:ro,z
  #     - /opt/pdm/nginx/certs:/etc/nginx/certs:ro,z
  #     - /data/pdm/logs/nginx:/var/log/nginx:z
```

### 7.3 关键字段解释

| 字段 | 作用 | 改动建议 |
| --- | --- | --- |
| `depends_on: mysql: condition: service_healthy` | 等 MySQL 健康检查通过后才启动 app | 不要改成 `service_started`，否则 Flyway 会连不上库 |
| `mysql.command` | 指定字符集 utf8mb4、时区 +08:00、最大连接数 200 | 中文与时区必须保留 |
| `mysql.healthcheck` | 用 `mysqladmin ping` 判活，`start_period: 40s` 给首次初始化留时间 | 首次启动初始化较慢，别把 retries 调太小 |
| `:z` 后缀 | SELinux 自动重标记宿主机目录，Enforcing 模式下容器才能读写 | CentOS 7 上务必保留 |
| `${APP_LISTEN:-0.0.0.0}:${APP_PORT:-8080}:8080` | `:-` 表示 `.env` 没配时用默认值；三段依次是「宿主机绑定地址:宿主机端口:容器端口」 | 想只本机访问把 `APP_LISTEN` 改成 `127.0.0.1`；宿主机 8080 被占就改 `APP_PORT` |
| `PDM_MASTER_KEY_FILE=/app/keys/master.key` | 告诉应用去哪读主密钥 | 与 `volumes` 的挂载点对应，别只改一边 |
| `SPRING_PROFILES_ACTIVE=prod` | 启用 `application-prod.yml`：日志写文件、关闭 Swagger | 调试时可临时改 `dev` |
| `restart: always` | 容器异常退出或宿主机重启后自动拉起 | 配合 `systemctl enable docker` 实现开机自启 |
| `image: pdm/delivery-server:1.0.0` | 构建产物的镜像名与 tag | 离线部署时 `docker save/load` 要用同一个 tag |
| `image: mysql:8.0.32` | 数据库镜像版本 | **别随手改成 `mysql:8.0` 最新 tag**：新镜像要求 CPU x86-64-v2，老虚拟化平台起不来，见 15.2 |

### 7.4 可选：Nginx 做 HTTPS

`deploy/docker-compose.yml` 末尾已备好注释掉的 nginx 服务，需要 HTTPS 或想统一走 80/443 时取消注释：

```yaml
  nginx:
    image: nginx:1.25-alpine
    container_name: pdm-nginx
    restart: always
    depends_on: [app]
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d:ro,z
      - /opt/pdm/nginx/certs:/etc/nginx/certs:ro,z
      - /data/pdm/logs/nginx:/var/log/nginx:z
```

站点配置已内置在仓库 `deploy/nginx/conf.d/pdm.conf`（compose 里的 `./nginx/conf.d` 相对于 compose 文件解析，正好指向该目录）：

```nginx
server {
    listen 80;
    server_name _;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name _;

    ssl_certificate     /etc/nginx/certs/pdm.crt;
    ssl_certificate_key /etc/nginx/certs/pdm.key;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_session_cache shared:SSL:10m;

    client_max_body_size 512m;

    location / {
        proxy_pass http://app:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 600s;
        proxy_send_timeout 600s;
        proxy_request_buffering off;
    }
}
```

生成内网自签证书：

```bash
mkdir -p /opt/pdm/nginx/certs /data/pdm/logs/nginx
cd /opt/pdm/nginx/certs
openssl req -x509 -nodes -days 3650 -newkey rsa:2048 \
  -keyout pdm.key -out pdm.crt -subj "/C=CN/O=Internal/CN=pdm.internal"
chmod 600 pdm.key
```

启用后：

```bash
cd /opt/pdm/src/deploy
vi docker-compose.yml        # 取消 nginx 段的注释
docker compose up -d
docker compose ps            # 三个服务都应为 Up
curl -kI https://127.0.0.1/  # -k 忽略自签证书告警，期望 301 或 200
```

浏览器首次访问自签证书会提示不安全，点「继续访问」即可；想去掉告警需要把 `pdm.crt` 导入到你电脑的受信任根证书。

启用 nginx 后建议把 `app` 的 `ports` 整段删掉——nginx 在 compose 内部网络里直连 `app:8080`，不需要再向宿主机发布，这样对外只暴露 443。

### 8.1 构建镜像

```bash
cd /opt/pdm/src/deploy
```

预期表现：

| 阶段 | 现象 | 耗时（首次） |
| --- | --- | --- |
| 拉基础镜像 | `Pulling fs layer` / `Download complete`，共 4 个镜像 | 2～8 分钟 |
| `npm install` | 大量 `added N packages` | 1～3 分钟 |

| 运行层 | `apt-get install wget tzdata` → `naming to ... pdm/delivery-server:1.0.0` | 30 秒 |

看到最后一行 `naming to docker.io/pdm/delivery-server:1.0.0  DONE` 就是构建成功。验证：

```bash
docker images | grep pdm
# pdm/delivery-server   1.0.0   xxxxxxxxxxxx   xx seconds ago   ~280MB
```

**构建失败怎么办**：


## 十、网络、防火墙与访问控制

### 10.1 必须先理解：firewalld 管不住 Docker 发布的端口

Docker 发布端口（compose 里的 `ports:`）是通过 iptables 的 `nat` 表 DNAT + `FORWARD` 链转发的，而 firewalld 的规则挂在 `INPUT` 链上。**流量根本不经过 INPUT，所以：**

- `firewall-cmd --add-port=8080/tcp` 对 Docker 发布的端口**没有必要**；
- `firewall-cmd --remove-port=8080/tcp` 也**拦不住**它。

想限制来源 IP，必须用 Docker 专用的 `DOCKER-USER` 链（Docker 保证不会覆盖这个链里的规则）。

### 10.2 用 DOCKER-USER 限制来源网段

```bash
# 1) 放行已建立连接的回包（必须放在最前面）
iptables -I DOCKER-USER -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT

# 2) 只允许管理网段访问 8080，其余来源丢弃（把网段换成你自己的）
iptables -I DOCKER-USER -p tcp --dport 8080 ! -s 192.168.1.0/24 -j DROP

# 3) 查看规则（DOCKER-USER 链默认最后有一条 RETURN，属正常）
iptables -L DOCKER-USER -n --line-numbers
```

让规则在重启后仍然生效：

```bash
yum install -y iptables-services
iptables-save > /etc/sysconfig/iptables
systemctl enable iptables
```

> 注意：`iptables-services` 与 `firewalld` 会互相接管规则，装完 `iptables-services` 后如果 firewalld 还在跑，建议二选一。个人自用机最简单的做法是：**只用 iptables 管 DOCKER-USER，SSH 端口靠云平台/路由器层面限制**。

验证限源生效：从网段外的机器 `curl http://虚拟机IP:8080/api/system/health` 应超时或被拒绝，网段内正常返回。

### 10.3 数据库端口

`3306` 发布在 `127.0.0.1`，只有虚拟机本机能连，**不需要也无法**通过防火墙进一步限制。验证：

```bash
ss -lntp | grep 3306
# 期望：127.0.0.1:3306  而不是 0.0.0.0:3306 或 *:3306
```

### 10.4 SSH 加固（可选，但强烈建议）

SSH 走 INPUT 链，firewalld 能正常管：

```bash
systemctl enable --now firewalld

# 只允许管理网段访问 22
firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="192.168.1.0/24" port port="22" protocol="tcp" accept'
firewall-cmd --reload
firewall-cmd --list-all
```

⚠️ **确认新规则下能正常 SSH 登录之后**，再考虑移除默认放行（否则可能把自己锁在外面）：

```bash
firewall-cmd --permanent --remove-service=ssh
firewall-cmd --reload
```

更稳妥的加固方式（不依赖防火墙）：改 SSH 端口、禁用密码登录改用密钥、`/etc/ssh/sshd_config` 里加 `AllowUsers 你的用户名`。

### 10.5 几种访问方式怎么选

| 场景 | 配置 | 访问地址 |
| --- | --- | --- |
| 局域网内自己电脑直接访问（默认） | `.env` 里 `APP_LISTEN=0.0.0.0` + 10.2 限源 | `http://虚拟机IP:8080` |
| 只想本机访问，通过 SSH 隧道用 | `.env` 里 `APP_LISTEN=127.0.0.1`，然后在你电脑上建隧道 | 见下方命令 |
| 想走标准 80/443 | 启用 7.4 的 nginx，删掉 app 的 `ports` 段 | `https://虚拟机IP` |
| 想换端口（比如 9090） | 改 compose 里 app 的 `ports` 为 `"${APP_LISTEN:-0.0.0.0}:9090:8080"` | `http://虚拟机IP:9090` |

SSH 隧道方式（Windows PowerShell 里执行，保持窗口开着）：

```powershell
ssh -L 8080:127.0.0.1:8080 root@虚拟机IP
# 然后浏览器访问 http://127.0.0.1:8080
```

这种方式最安全：8080 完全不对外发布，流量全程走 SSH 加密。缺点是每次都要先开隧道。

## 十一、备份与恢复

### 11.1 备份什么

| 对象 | 位置 | 怎么备 | 丢失后果 |
| --- | --- | --- | --- |
| 数据库 | `/data/pdm/mysql` | `mysqldump` 逻辑备份 | 项目/文档/凭据元数据全丢 |
| 附件 | `/data/pdm/uploads` | tar 打包 | 文档正文与凭据加密附件丢失 |
| 主密钥 | `/data/pdm/keys/master.key` | **手工离线备份，脚本不管** | 所有已存密码永久无法解密 |
| 配置 | `/opt/pdm/src/deploy/.env` | 建议一并抄一份到密码管理器 | 口令丢失，恢复后应用连不上库 |

> 为什么脚本不备主密钥？因为备份目录和密钥在同一台机器上，一起备等于没备（磁盘坏了两个都没）。密钥必须**离线**、**异地**保存。

### 11.2 备份脚本

仓库已内置 `deploy/backup.sh`：数据库每天全备并 gzip，附件每周日全备；数据库备份保留 14 天、附件保留 8 份；结束时会提示主密钥不在备份范围内。脚本**原地运行**即可，会自动读取同目录的 `.env`。

可用环境变量覆盖的参数：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `ENV_FILE` | 脚本同目录 `.env`，回退 `/opt/pdm/.env` | 提供 `MYSQL_ROOT_PASSWORD`、`DB_NAME` |
| `BACKUP_DIR` | `/data/pdm/backup` | 备份输出目录 |
| `DB_CONTAINER` | `pdm-mysql` | MySQL 容器名 |
| `UPLOAD_DIR` | `/data/pdm/uploads` | 附件目录 |
| `DB_NAME` | `pdm` | 库名（`.env` 里配了就以 `.env` 为准） |
| `KEEP_DB_DAYS` | `14` | 数据库备份保留天数 |
| `KEEP_FILE_COPIES` | `8` | 附件备份保留份数 |

```bash
chmod +x /opt/pdm/src/deploy/backup.sh

# 手动跑一次验证
/opt/pdm/src/deploy/backup.sh

# 看产物
ls -lh /data/pdm/backup/db /data/pdm/backup/files

# 配 cron：每天 02:00
crontab -e
```

加入这一行：

```
0 2 * * * /opt/pdm/src/deploy/backup.sh >> /data/pdm/logs/backup-cron.log 2>&1
```

确认 cron 服务在跑：

```bash
systemctl enable --now crond
crontab -l
tail -f /data/pdm/logs/backup-cron.log      # 第二天检查
```

### 11.3 恢复步骤

```bash
cd /opt/pdm/src/deploy
source .env

# 0) 停应用，避免恢复过程中有写入
docker compose stop app

# 1) 确保 MySQL 在跑
docker compose up -d mysql && sleep 20
docker compose ps mysql                     # 应为 healthy

# 2) 导入数据库（把日期换成实际备份文件名）
gunzip -c /data/pdm/backup/db/${DB_NAME}_2026-10-10.sql.gz \
  | docker exec -i pdm-mysql sh -c "exec mysql -uroot -p'$MYSQL_ROOT_PASSWORD' $DB_NAME"

# 3) 还原附件并修正属主（容器内以 uid 1000 运行）
tar -xzf /data/pdm/backup/files/uploads_2026-10-10.tar.gz -C /data/pdm
chown -R 1000:1000 /data/pdm/uploads

# 4) 放回主密钥（从离线副本写回）
vi /data/pdm/keys/master.key                # 粘贴 44 字符的 Base64，保存
chown 1000:1000 /data/pdm/keys/master.key
chmod 600 /data/pdm/keys/master.key

# 5) 启动应用并验证
docker compose up -d app
docker compose logs -f app | grep -E '主密钥|Successfully|Started'
curl -s http://127.0.0.1:8080/api/system/health
```

**必须做的最后一步验证**：登录系统 → 打开任意一条凭据 → 点「眼睛」查看明文。

- 能看到正确明文 → 恢复成功。
- 报「密文解密失败，请确认 master.key 是否为加密时使用的密钥」→ 第 4 步的密钥不对，必须找回原密钥，否则历史凭据不可恢复。

补充说明：

- 备份里已包含 `flyway_schema_history` 表，恢复后 Flyway 会跳过历史迁移，日志里看不到 `Migrating schema` 是正常的。
- 只想恢复单个项目/单条凭据？可以把 SQL 备份解到临时库再挑数据：`gunzip -c xxx.sql.gz | mysql -uroot -p tmpdb`。

### 11.4 迁移到另一台机器

```bash
# 旧机器
/opt/pdm/src/deploy/backup.sh                          # 强制跑一次（附件只在周日备，可临时改脚本或手工 tar）
tar -czf /tmp/pdm-uploads.tar.gz -C /data/pdm uploads
scp /data/pdm/backup/db/*.sql.gz /tmp/pdm-uploads.tar.gz root@新机器IP:/tmp/
# 另外单独安全传输 master.key 和 .env（不要用明文邮件/聊天工具）

# 新机器：先按第一～七章装好 Docker、建好目录
scp /tmp/pdm-uploads.tar.gz ...
tar -xzf /tmp/pdm-uploads.tar.gz -C /data/pdm && chown -R 1000:1000 /data/pdm/uploads
# 写回 master.key 与 .env，然后按 11.3 的第 1、2、5 步导入并启动
```

新机器上代码可以用 `git clone` 重新拉，或者把整个 `/opt/pdm/src` 一起拷过去。

### 11.5 主密钥丢了 / 想换密钥怎么办

| 情况 | 处理方式 |
| --- | --- |
| 密钥丢了，但有旧密钥的离线副本 | 写回副本即可，见 11.3 第 4 步 |
| 密钥彻底丢了 | 数据库里的密文永久无法解密。只能在系统里逐条重新录入凭据密码（新建时会用新密钥加密）。项目信息、文档、审计日志不受影响 |
| 想主动换密钥（例如怀疑泄露） | 当前版本不支持自动重加密。做法：用旧密钥把每条凭据的明文导出 → 换 `master.key` → 逐条重新保存。建议等业务空窗期做，做完立刻做全量备份 |

## 十二、日常运维速查

所有命令都在 `/opt/pdm/src/deploy` 目录下执行（先 `cd /opt/pdm/src/deploy`）。

### 12.1 服务控制

| 目的 | 命令 |
| --- | --- |
| 看状态 | `docker compose ps` |
| 启动 | `docker compose up -d` |
| 停止（保留容器） | `docker compose stop` |
| 重启单个服务 | `docker compose restart app` |
| 停止并删除容器（**数据不丢**） | `docker compose down` |
| 停止并删除容器**和数据卷** | `docker compose down -v` ⚠️ 本项目数据在 bind mount 里，`-v` 不会删 `/data/pdm`，但仍不建议随手用 |
| 重建并重启（改了代码后） | `docker compose up -d --build` |
| 只重建 app | `docker compose build app && docker compose up -d app` |

> `down` 与 `stop` 的区别：`stop` 只停进程，容器还在；`down` 会删掉容器和网络。两者都**不会**删除 `/data/pdm` 下的数据（因为用的是 bind mount 而不是 named volume）。

### 12.2 看日志

| 目的 | 命令 |
| --- | --- |
| 实时跟随 app 日志 | `docker compose logs -f app` |
| 最近 200 行 | `docker compose logs --tail 200 app` |
| 只看错误 | `docker compose logs app \| grep -iE 'error\|exception' \| tail -50` |
| MySQL 日志 | `docker compose logs -f mysql` |
| 应用文件日志（含滚动历史） | `ls -lh /data/pdm/logs/` → `tail -f /data/pdm/logs/delivery-server.log` |
| 容器 stdout（json-file） | `ls -lh /var/lib/docker/containers/*/*-json.log` |
| 备份任务日志 | `tail -50 /data/pdm/logs/backup-cron.log` |

日志级别在 `application-prod.yml` 里配置（默认 `root: WARN`、`com.pdm: INFO`）。想临时开 DEBUG：

```bash
vi /opt/pdm/src/delivery-server/src/main/resources/application-prod.yml
# com.pdm: DEBUG
docker compose build app && docker compose up -d app
```

### 12.3 进容器排查

```bash
# 进 app 容器（非 root 用户 pdm）
docker exec -it pdm-app bash
whoami                       # pdm
ls -l /app                   # app.jar  logs  uploads  keys
ls -l /app/keys/master.key   # 只读，-r--------
cat /app/keys/master.key     # 能读到说明挂载正常
df -h /app/uploads
exit

# 进 MySQL 容器
source .env
docker exec -it pdm-mysql mysql -u"$DB_USER" -p"$MYSQL_PASSWORD" "$DB_NAME"
# 常用 SQL
#   show tables;
#   select id,project_no,name,status,archived from biz_project order by id desc limit 10;
#   select id,platform_name,username,expire_date from biz_credential;
#   select * from v_expire_alert where days_left <= 30;
#   select id,username,module,action,success,create_time from sys_audit_log order by id desc limit 20;
#   select cfg_key,cfg_value from sys_config;
#   exit
```

⚠️ **绝对不要**用 SQL 直接改 `biz_credential.secret_cipher`——那是密文，手工改会导致解密失败。要改密码请走系统界面。

### 12.4 磁盘与资源

```bash
df -h /data /var/lib/docker           # 磁盘余量
du -sh /data/pdm/*                    # 各目录占用
du -sh /data/pdm/uploads/*            # 按项目看附件占用
docker system df                      # 镜像/容器/构建缓存占用
docker system prune -f                # 清理无用镜像与停止的容器（不会碰数据卷）
docker builder prune -f               # 清理构建缓存（下次构建会变慢）
docker stats --no-stream              # 实时 CPU/内存占用
```

容器内存上限已由 `.env` 的 `APP_MEM_LIMIT` 控制（对应 compose 里的 `mem_limit`，默认 `1g`）。**这个上限不能省**：JVM 用 `-XX:MaxRAMPercentage=70` 计算堆大小，没有容器上限时它会按宿主机总内存的 70% 来算，2～4 GB 的虚拟机上很容易和 MySQL 抢内存被 OOMKilled。

改完要重建容器才生效：

```bash
vi .env                     # 例如 APP_MEM_LIMIT=2g
docker compose up -d app    # compose 检测到配置变化会自动重建
docker inspect pdm-app --format '{{.HostConfig.Memory}}'    # 字节数，2g = 2147483648
```

### 12.5 数据表增长与清理

单人使用十年内单表都不会超过 10 万行，**不需要**定期清理。增长最快的是 `sys_audit_log`（每次查看明文、复制、下载都记一条）。真要清理时：

```bash
source .env
# 先备份
/opt/pdm/src/deploy/backup.sh
# 删除一年前的审计日志（谨慎，审计链会断）
docker exec -it pdm-mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" "$DB_NAME" \
  -e "DELETE FROM sys_audit_log WHERE create_time < DATE_SUB(NOW(), INTERVAL 365 DAY);"
```

## 十三、升级与回滚

### 13.1 升级前必做

```bash
cd /opt/pdm/src/deploy
./backup.sh                                   # 全量备份
docker compose ps > /tmp/pdm-before.txt       # 记录当前状态
docker images | grep pdm >> /tmp/pdm-before.txt   # 记录当前镜像 tag
```

### 13.2 执行升级

```bash
cd /opt/pdm/src
git pull                                      # 或重新拷贝代码覆盖（保留 deploy/.env！）
cd deploy
docker compose build app                      # 只重建应用镜像，MySQL 不动
docker compose up -d app
docker compose logs -f app | grep -iE 'flyway|migrat|Started PdmApplication'
```

日志判读：

| 日志 | 含义 |
| --- | --- |
| `Current version of schema ... : 2` 且没有 `Migrating` | 本次升级没有数据库变更，正常 |
| `Migrating schema ... to version "3 - xxx"` → `Successfully applied 1 migration` | 有新的迁移脚本并已执行 |
| `Migration ... failed` / `Validate failed` | **迁移失败**，立刻按 13.3 回滚 |

浏览器强刷（`Ctrl+F5`）确认前端也是新版本，然后点几个核心页面验证。

### 13.3 回滚

```bash
cd /opt/pdm/src/deploy

# 1) 恢复数据库（用升级前那次备份）
source .env
docker compose stop app
gunzip -c /data/pdm/backup/db/${DB_NAME}_$(date +%F).sql.gz \
  | docker exec -i pdm-mysql sh -c "exec mysql -uroot -p'$MYSQL_ROOT_PASSWORD' $DB_NAME"

# 2) 代码回退
cd /opt/pdm/src && git log --oneline -5 && git checkout <上一个可用 commit>

# 3) 用旧代码重建镜像并启动
cd deploy && docker compose build app && docker compose up -d app
docker compose logs -f app | grep -E 'Successfully|Started'
```

> 提前给稳定版本打 tag 会让回滚更快：`docker tag pdm/delivery-server:1.0.0 pdm/delivery-server:stable`，回滚时直接改 compose 的 `image:` 为 `stable` 再 `up -d`，不用重新构建。

### 13.4 数据库结构变更的规矩

- 一律新增 Flyway 迁移脚本：`delivery-server/src/main/resources/db/migration/V{n}__{说明}.sql`，`n` 递增（当前最后一个是 `V3`，下一个是 `V4`）。
- **禁止**修改已执行过的历史脚本（`V1`/`V2`/`V3`…）——Flyway 会校验 checksum，改了会导致启动失败（`Validate failed: Migration checksum mismatch`）。
- **禁止**在生产库手工执行 DDL，否则 Flyway 的版本记录与实际结构会不一致。
- 万一不小心改了历史脚本导致 checksum 报错：把文件改回原样，或者（数据可丢的情况下）清空库重来。

## 十四、离线（内网无外网）部署

### 14.1 总体思路

镜像构建需要联网下载 node/maven 基础镜像与依赖，**不要在离线机器上构建**。做法是：在一台能联网的同架构机器上构建好 → `docker save` 导出 tar → 拷贝到虚拟机 → `docker load` 导入。

### 14.2 在联网机器上准备

要求：Linux x86_64 + Docker；或 Windows/Mac 装 Docker Desktop（Mac M 系列必须加 `--platform linux/amd64`）。

```bash
cd /path/to/repo                     # 仓库根目录
docker pull mysql:8.0.32
docker build -f deploy/Dockerfile -t pdm/delivery-server:1.0.0 .
docker save -o pdm-images.tar mysql:8.0.32 pdm/delivery-server:1.0.0
ls -lh pdm-images.tar                # 约 900MB
sha256sum pdm-images.tar > pdm-images.tar.sha256
```

### 14.3 拷贝并导入

需要拷贝到虚拟机的东西：

| 文件/目录 | 用途 |
| --- | --- |
| `pdm-images.tar` + `.sha256` | 镜像 |
| 整个仓库（至少 `deploy/` 目录） | compose、.env.example、nginx 配置、backup.sh |
| Docker 的 rpm 包（若虚拟机还没装 Docker） | 见 14.4 |

```bash
# 校验完整性
sha256sum -c pdm-images.tar.sha256

# 导入镜像
docker load -i pdm-images.tar
docker images | grep -E 'pdm|mysql'

# 启动（--no-build 确保不触发本地构建）
cd /opt/pdm/src/deploy
docker compose up -d --no-build
```

compose 里 `image: pdm/delivery-server:1.0.0` 与 `save` 时的 tag 一致，会直接命中本地镜像。

### 14.4 离线安装 Docker 本身

在联网机器上下载 rpm（版本与 3.1 一致）：

```bash
yum install -y yum-utils
yumdownloader --resolve --destdir=/tmp/docker-rpms \
  docker-ce-24.0.7 docker-ce-cli-24.0.7 containerd.io docker-compose-plugin
ls /tmp/docker-rpms
```

拷到虚拟机后：

```bash
cd /tmp/docker-rpms
yum localinstall -y ./*.rpm
systemctl enable --now docker
docker compose version
```

或者用静态二进制包（不依赖 rpm）：从 `https://download.docker.com/linux/static/stable/x86_64/` 下载 `docker-24.0.7.tgz`，解压后把可执行文件放进 `/usr/local/bin`，再手写 systemd unit。这种方式 compose 插件需要另外下载 `docker-compose-linux-x86_64`（GitHub Releases），放到 `/usr/local/lib/docker/cli-plugins/docker-compose` 并 `chmod +x`。

## 十五、常见问题排查（FAQ）

### 15.1 构建类

| 现象 | 原因与处理 |
| --- | --- |
| `docker compose build` 卡在 `npm install` | Dockerfile 已指定 npmmirror 源。先在 VM 上 `curl -I https://registry.npmmirror.com` 验证能否出网；不行就走第十四章离线路径 |
| `npm ERR! network timeout` / `ETIMEDOUT` | 同上，属出网问题；也可给 Docker 配代理：`/etc/systemd/system/docker.service.d/http-proxy.conf` 里写 `Environment="HTTP_PROXY=..."`，然后 `systemctl daemon-reload && systemctl restart docker` |
| 卡在 `Downloading from central` 不动（连接建立但无数据、CPU 也不动） | 出口网络对境外 CDN「握手后黑洞」：容器 netns 里 `ss -tnp` 能看到 ESTAB 但 Recv-Q/Send-Q 全 0。本项目已在 `deploy/maven-settings.xml` 内置阿里云镜像（`mirrorOf=central`），正常不会遇到；若你删过 Dockerfile 里那行 `COPY deploy/maven-settings.xml`，加回去 |
| 构建到一半被 kill / `exit code 137` | 内存不足（OOM）。见 0.3 加 swap，或给虚拟机加内存 |
| `failed to solve: failed to read dockerfile` | 构建上下文不对。必须在**仓库根目录**执行，或直接用 `cd deploy && docker compose build`（compose 已配好 `context: ..`） |
| `mvn` 报 `Could not resolve dependencies for project ... spring-boot-starter-parent:pom:3.2.5` | 网络中断导致依赖不完整。`docker builder prune -f` 后重新构建 |
| `error pulling image configuration` | 镜像加速地址失效。编辑 `/etc/docker/daemon.json` 换 `registry-mirrors`，重启 docker |

### 15.2 启动类

| 现象 | 原因与处理 |
| --- | --- |
| 容器反复重启，日志报 `主密钥文件不存在` | `/data/pdm/keys/master.key` 没建或没挂载。检查文件是否存在、compose 里 `volumes` 那行是否被改过 |
| 日志报 `AccessDeniedException: /app/keys/master.key` | 主密钥属主不对：容器内 app 以 uid 1000 运行，文件却是 `root:root` + `600`。`chown 1000:1000 /data/pdm/keys/master.key` 后 `docker compose restart app` |
| 日志报 `主密钥必须是 32 字节` | `openssl rand -base64 32` 生成的才是对的；手工编的字符串长度不对 |
| 日志报 `Communications link failure` / `Access denied for user` | `.env` 里的 `MYSQL_PASSWORD` 与 MySQL 首次初始化时写入的不一致。**注意：MySQL 只在数据目录为空时读环境变量**，改口令要进容器 `ALTER USER` 或清空 `/data/pdm/mysql` 重来 |
| MySQL 容器起不来，日志 `Permission denied` on `/var/lib/mysql` | 属主不是 999。`chown -R 999:999 /data/pdm/mysql`；仍不行看 1.4 的 SELinux |
| `Fatal glibc error: CPU does not support x86-64-v2` | 新版 `mysql:8.0` 镜像基于 Oracle Linux 9，glibc 要求 CPU 微架构 ≥ v2，超融合 / KVM 默认 vCPU 只暴露 baseline。compose 已钉 `mysql:8.0.32`（OL8 基础，v1 可跑）；若换过镜像仍报，去虚拟化平台把 vCPU 模型改为 host-passthrough |
| MySQL 日志 `[ERROR] InnoDB: Unable to lock ./ibdata1` | 有残留进程或宿主机上还跑着另一个 MySQL。`systemctl stop mysqld mariadb` |
| `Flyway ... Validate failed` | 有人改了已执行过的历史迁移脚本（V1/V2/V3…）。见 13.4 |
| app 起来但 `curl /api/system/health` 返回 `{"status":"DOWN","db":false}` | 数据库连不上，按上面两条查 |
| 日志有 `Port 8080 was already in use` | 宿主机 8080 被占。`ss -lntp \| grep 8080` 找到占用者，或改 compose 里的宿主端口 |
| 容器一直 `health: starting` 不变 healthy | 前 90 秒属正常。超过 3 分钟就 `docker inspect pdm-app --format '{{json .State.Health}}'` 看探测输出；确认镜像里有 `wget`（本项目 Dockerfile 已安装） |
| 页面能打开但所有接口 401 | `JWT_SECRET` 变了（旧 Token 全部失效），或虚拟机时间漂移导致 Token 立即过期。见 1.2 |
| 登录后立刻被踢回登录页 | 同上；另外确认浏览器 localStorage 没被禁用 |

### 15.3 使用类

| 现象 | 原因与处理 |
| --- | --- |
| 下拉框「无数据」、页面行为怪异，但无痕窗口一切正常 | 旧标签页还跑着上一次构建的前端包：重新构建后 chunk 哈希已变，旧标签页请求旧文件名会 404。`Ctrl+Shift+R` 强刷或关掉标签重开即可。本项目已对 `index.html` 设 `no-store`、对 `/assets/**` 设一年强缓存，升级后正常不会再遇到 |
| 浏览器打不开 `http://虚拟机IP:8080` | 按顺序查：① `.env` 里 `APP_LISTEN=0.0.0.0`；② `docker compose ps` 中 app 是 Up；③ VM 本机 `curl 127.0.0.1:8080/api/system/health` 是否通；④ `iptables -L DOCKER-USER -n` 是否 DROP 了你的网段；⑤ `ip addr` 确认 IP 没搞错 |
| 登录总提示「验证码错误」 | 验证码存在应用内存里，容器重启后全部失效，刷新页面重新获取即可；不想用就在 `.env` 设 `CAPTCHA_ENABLED=false` 后 `docker compose up -d app` |
| 提示「账号已锁定，请 N 分钟后重试」 | 密码连续错 5 次（`login.failLimit`）。管理员可在「用户管理」里点「解锁」，或等 15 分钟（`login.lockMinutes`） |
| 查看凭据明文报「无查看凭据明文的权限」 | 当前账号的 `can_view_secret` 是关的。用 admin 在「用户管理」里打开「查看明文」开关 |
| 查看明文报「密文解密失败」 | `master.key` 被换过或没挂载上。见 11.5 |
| 上传大文件报 413 | 三处限制取最小值：nginx `client_max_body_size`（默认 512m）、Spring `spring.servlet.multipart.max-file-size`（512MB）、系统参数 `upload.maxSizeMb`（默认 500） |
| 凭据附件传不上去，提示超过上限 | 凭据附件默认限 20MB（`cred.attachment.maxSizeMb`）。大文件请走「交付文档」上传 |
| 下载的中文文件名乱码 | 确认容器 `LANG=C.UTF-8`（Dockerfile 已设）、数据库为 utf8mb4（compose 已设）、浏览器不是 IE |
| 页面样式错乱 / 白屏 | 前端资源缓存问题，`Ctrl+F5` 强刷；仍不行 `docker compose build app && docker compose up -d app` 重建 |
| 时间显示差 8 小时 | 容器 `TZ` 未生效或宿主机时间不对。`docker exec pdm-app date` 与 `date` 对比 |

### 15.4 性能与稳定性

| 现象 | 处理 |
| --- | --- |
| 磁盘增长快 | `docker system df` 看构建缓存；`docker builder prune -f`。再查 `/data/pdm/logs` 与容器 json-file 日志上限（3.4） |
| app 内存持续上涨 | `docker stats` 观察；JVM 已限 `MaxRAMPercentage=70`。真泄漏就 `docker compose restart app`（重启后需重新登录） |
| 列表页变慢 | 单人使用几乎不会。真慢了先 `EXPLAIN` 看 SQL，检查索引是否命中（docs/02 第七章有索引说明） |

## 十六、上线安全检查清单

部署完成后逐项打勾：

- [ ] `deploy/.env` 权限 600，未提交 Git，4 个口令都是强随机值（不含 `change-me`）
- [ ] `/data/pdm/keys/master.key` 权限 600、属主 1000:1000，**且已做至少一份离线副本**

- [ ] `JWT_SECRET` 不是 `.env.example` 里的示例值
- [ ] 已启用 HTTPS，或明确接受内网 HTTP 风险
- [ ] 备份 cron 已配置，且**完整做过一次恢复演练**（含凭据明文可解密）
- [ ] 宿主机时间同步已开启（`timedatectl` 显示 synchronized: yes）
- [ ] `systemctl is-enabled docker` 为 `enabled`，容器 `restart: always`
- [ ] MySQL root 不允许远程登录（默认就是，确认没人改过）
- [ ] SSH 已限制来源，或已改为密钥登录
- [ ] `docker compose logs app` 里没有 ERROR / Exception 堆积

## 附录 A：不用 Docker，直接跑 jar（调试或备选方案）

Docker 出问题时可以用这种方式快速验证「代码本身能不能跑」。需要宿主机装 JDK 17 和 MySQL 8。

### A.1 构建 jar

```bash
# 有 Maven 的机器上
cd /opt/pdm/src/delivery-server
mvn clean package -DskipTests
```

### A.4 用 systemd 托管（长期运行）

```bash
useradd -r -u 1000 -s /sbin/nologin pdm
chown -R pdm:pdm /data/pdm/uploads /data/pdm/logs
mkdir -p /opt/pdm/app
cp /opt/pdm/src/delivery-server/target/delivery-server.jar /opt/pdm/app/app.jar

cat > /etc/pdm.env <<'EOF'
DB_HOST=127.0.0.1
DB_PORT=3306
DB_NAME=pdm
DB_USER=pdm
DB_PASSWORD=你的强口令
PDM_MASTER_KEY_FILE=/data/pdm/keys/master.key
PDM_UPLOAD_DIR=/data/pdm/uploads
PDM_JWT_SECRET=64位随机串
PDM_INIT_PASSWORD=Admin@12345
SPRING_PROFILES_ACTIVE=prod
EOF
chmod 600 /etc/pdm.env

cat > /etc/systemd/system/pdm.service <<'EOF'
[Unit]
Description=Project Delivery Manager
After=network.target mysqld.service
Wants=mysqld.service

[Service]
Type=simple
User=pdm
Group=pdm
EnvironmentFile=/etc/pdm.env
WorkingDirectory=/opt/pdm/app
ExecStart=/usr/bin/java -XX:MaxRAMPercentage=70 -Djava.security.egd=file:/dev/./urandom -jar /opt/pdm/app/app.jar
SuccessExitStatus=143
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
EOF

systemctl daemon-reload
systemctl enable --now pdm
systemctl status pdm --no-pager
journalctl -u pdm -f          # 看日志
```
